## 3. 多模态输入

作用：

- 支持用户消息中的 `text + image`
- 支持模型通过工具读取图片后继续分析
- 保持 OpenAI 与 Anthropic 的能力模型一致

当前实现原则：

- 多模态的一等公民仍然是共享消息模型，而不是通用附件系统
- 用户附图直接进入 `user message content blocks`
- 工具返回图片时，先持久化在 `tool_result.content`
- provider 侧继续只发送标准文本型 `tool_result.output`
- runtime 再把 `tool_result.content` 中的图片重建为下一轮临时 `user image message`

这一层的关键取舍是：

- 不依赖 Anthropic 专有的“图片型 tool_result”协议
- 不为 OpenAI 额外发明 provider-specific shim
- 统一通过 runtime 注入标准图片消息，保证两家 provider 共享同一条主路径

对长会话的影响也要一并明确：

- `tool_result.content` 会跟随 session 持久化
- `resume` 后 runtime 会重新扫描历史并恢复临时图片消息
- `compact` 后同样可以从持久化历史恢复图片上下文
- 因此当前不需要额外补一套专门的 post-compact image recovery 机制

当前已完成的第一阶段范围：

- 共享 `image block` 消息模型
- Anthropic / OpenAI 的用户图片输入
- `WebFetch` 远程图片读取
- 工具图片结果的 runtime 注入式继续分析
- transcript / history / verbose 的受控图片摘要

当前仍未进入主线的范围：

- 本地图片读取工具
- interactive 图片输入
- `--print --image`
- 更通用的 attachment / upload 抽象

## 4. 执行组织能力

### 4.1 Plan / Task

作用：

- 在复杂任务中显式管理执行步骤
- 支持 plan mode
- 支持任务状态跟踪

这是 Claude Code 成熟度很重要的一层，不应省略。

对齐 Claude Code 当前源码，`plan mode` 应按下面的产品规则实现：

- `plan mode` 可以由模型主动建议或发起进入请求，但不应由模型静默切换当前主会话状态
- `EnterPlanMode` 直接进入 planning；进入 planning 本身不是 approval step。用户显式输入 `/plan` 也可直接进入
- `ExitPlanMode` 负责展示 plan 并结束高约束 planning；它不是交互式审批点，也不会在用户选择后立即实施
- `plan mode` 的价值不只在于禁止写文件，而在于切换模型的工作节奏：
  - 先探索代码库
  - 识别已有模式和风险
  - 必要时发起澄清问题
  - 产出结构化 plan / task breakdown
  - 交付 plan 后等待用户下一步
- `task / current step` 应是会话级状态，而不是散落在 transcript 里的普通文本
- `resume` 后需要能恢复当前是否处于 `plan mode`、当前任务、task 列表和当前步骤

因此这一阶段的重点应是“planning 作为执行控制层的一部分”，而不是项目级 plan 看板或多计划总览。

另外，若要在 `Task*` 上对齐 Claude Code 当前源码，还需要补一条实现原则：

- `TaskCreate / TaskList / TaskGet / TaskUpdate` 的详细使用规则，应主要来自 tool prompt
- 不应把 task tool 的细粒度工作流大量堆进全局 system prompt
- 也就是说，这一层不是只做 task store 和 tool 接口，还要补“模型如何被教会正确使用这些 tool”的提示链路

同样地，若要在 `plan mode` 的 runtime 行为上继续对齐 Claude Code 当前源码，也应遵循下面的实现原则：

- plan-mode carry-over 与 planning 提醒，应优先走 attachment-style runtime message，而不是继续膨胀全局 system prompt
- compact 后第一轮如果仍处于 `plan mode`，应强制补一次 full planning reminder，避免 compact 后丢失 planning 语义
- `dclaw` 当前已实现的最小近似，是通过临时 `<system-reminder>` user meta message 注入：
  - `plan_mode`
  - `plan_mode_exit`
  - `plan_mode_reentry`
  - post-compact first-turn full `plan_mode`
- 这些提醒当前主要以当轮 prompt 的 attachment-style runtime message 生效，不再额外持久化到 transcript。后续再继续收敛到更完整的结构化 attachment / runtime 恢复语义

详细落地方案见：

- [plan-task-spec.md](./plan-task-spec.md)
