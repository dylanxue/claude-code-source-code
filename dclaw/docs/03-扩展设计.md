## 3. 执行组织能力

### 3.1 Plan / Task

作用：

- 在复杂任务中显式管理执行步骤
- 支持 plan mode
- 支持任务状态跟踪

这是 Claude Code 成熟度很重要的一层，不应省略。

对齐 Claude Code 当前源码，`plan mode` 应按下面的产品规则实现：

- `plan mode` 可以由模型主动建议或发起进入请求，但不应由模型静默切换当前主会话状态
- 真正切换到 `plan mode` 时，需要用户确认；用户显式输入 `/plan` 则可直接进入
- `plan mode` 的价值不只在于禁止写文件，而在于切换模型的工作节奏：
  - 先探索代码库
  - 识别已有模式和风险
  - 必要时发起澄清问题
  - 产出结构化 plan / todo
  - 等待批准后再退出并实施
- `task / todo / current step` 应是会话级状态，而不是散落在 transcript 里的普通文本
- `resume` 后需要能恢复当前是否处于 `plan mode`、当前任务、todo 列表和当前步骤

因此这一阶段的重点应是“planning 作为执行控制层的一部分”，而不是项目级 plan 看板或多计划总览。

另外，若要在 `Task*` 上对齐 Claude Code 当前源码，还需要补一条实现原则：

- `TaskCreate / TaskList / TaskGet / TaskUpdate` 的详细使用规则，应主要来自 tool prompt
- 不应把 task tool 的细粒度工作流大量堆进全局 system prompt
- 也就是说，这一层不是只做 task store 和 tool 接口，还要补“模型如何被教会正确使用这些 tool”的提示链路

同样地，若要在 `plan mode` 的 runtime 行为上继续对齐 Claude Code 当前源码，也应遵循下面的实现原则：

- plan-mode carry-over 与 planning 提醒，应优先走 attachment-style runtime message，而不是继续膨胀全局 system prompt
- compact 后第一轮如果仍处于 `plan mode`，应强制补一次 full planning reminder，避免 compact 后丢失 planning 语义
- `dclaw` 当前已实现的最小近似，是通过临时 `<system-reminder>` user meta message 注入：
  - `plan_mode`
  - `plan_mode_exit`
  - `plan_mode_reentry`
  - post-compact first-turn full `plan_mode`
- 这些提醒当前只作用于当轮 prompt，不写回 transcript；后续再继续收敛到更完整的结构化 attachment / runtime 恢复语义

详细落地方案见：

- [plan-task-spec.md](./plan-task-spec.md)

## 7. 后置场景能力

### 7.1 Coding 场景增强

这是后续场景层，而不是核心主架构的一部分。

可包含：

- repo/workspace 感知
- 开发任务工作流增强
- 代码场景下的 prompt/tool 组合优化

## 8. 实施顺序

建议顺序：

1. compact
2. plan / task / todo
3. memory
4. 多代理 / worktree
5. MCP
6. skills
7. plugins
8. remote / structured IO
9. coding 场景增强
